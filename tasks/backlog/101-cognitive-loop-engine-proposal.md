## Proposal: Cognitive Loop Engine — Automated Brain↔Hands Orchestration

### Executive Summary

The Cognitive Loop Engine is a local orchestration daemon that eliminates the manual copy-paste workflow between the Orchestrator (Brain) and OpenCode/Freebuff (Hands). It routes `system-prompt.md` directly to LLM APIs, invokes the Hands programmatically, and maintains Manager approval gates via Telegram or a local dashboard. The Manager transitions from "data entry operator copying XML blocks" to "executive approving decisions via buttons."

### Component Specifications

#### 1. Kanban Watcher

- Detects new task files in `tasks/backlog/` and triggers the pipeline.
- Mechanism: Python `watchdog` filesystem observer.
- Trigger: New `.md` file created → parse task metadata → send to LLM Router.
- Constraint: Read-only. Never modifies task files.

#### 2. LLM Router

- Sends `system-prompt.md` + task context to the configured LLM API.
- Mechanism: Direct HTTP calls to LLM provider APIs (Gemini, Claude, Qwen, OpenAI).
- System Prompt: Reads `system-prompt.md` from disk at each invocation (always current version).
- Response Parsing: Extracts the Architect's Blueprint (Markdown) or `<hands_implementation_task>` XML from the LLM response.
- Persona Routing: Appends persona-specific system instructions based on the current pipeline stage (Architect → QA Engineer → Code Reviewer).

#### 3. Approval Gateway

- Pauses the pipeline at Step 3 (Plan Approval) and Step 8 (PO Closure) for Manager sign-off.
- Mechanism (Telegram): Sends a Telegram message with an "Approve" / "Reject" inline keyboard. Manager taps a button. Engine resumes.
- Mechanism (Dashboard): Local Streamlit/Gradio web UI renders the plan. Manager clicks "Approve Plan" or "Approve Closure."
- ZAC Enforcement: No task proceeds to Hands execution or closure without explicit Manager approval. The engine cannot bypass this gate.

#### 4. Hands Executor

- Invokes OpenCode programmatically with the generated `<hands_implementation_task>` XML.
- Mechanism: OpenCode CLI invocation via `subprocess` or OpenCode SDK (if available).
- Input: The XML task block generated by the LLM Router.
- Output: Captures OpenCode's stdout/stderr and reads the resulting `tasks/qa/` task file.
- ZAC Compliance: OpenCode's own ZAC guardrails remain intact. The engine does not inject `git commit` or `git push` commands.

#### 5. QA Loop Engine

- After Hands execution completes, sends the task file back to the LLM API for QA Engineer and Code Reviewer personas.
- Mechanism: Reads `tasks/qa/<task-file>.md`, sends to LLM API with QA Engineer system instructions, receives QA report, then sends to Code Reviewer.
- Loop: If QA_REJECTED or REJECTED_NEEDS_FIXES → generate fix task → loop back to Hands Executor.

#### 6. State Machine

- Tracks each task's position in the pipeline.
- States: `BACKLOG → PLANNING → AWAITING_APPROVAL → IMPLEMENTING → QA → REVIEW → AWAITING_CLOSURE → CLOSED`
- Persistence: SQLite database or JSON state file in `.loop-engine/state/`.
- Recovery: On daemon restart, resume from last known state.

### Technology Stack

| Component | Technology | Rationale |
|---|---|---|
| Daemon runtime | Python 3.12+ | Matches existing MCP server stack; `uv` for dependency management |
| LLM API calls | `litellm` or direct `httpx` | Multi-provider support (Gemini, Claude, Qwen, OpenAI) |
| File watching | `watchdog` | Reliable filesystem observer |
| Telegram notifications | `python-telegram-bot` | Existing Telegram integration in the workflow |
| Local dashboard | Streamlit (Phase 2) | Rapid prototyping; no frontend build step |
| State persistence | SQLite via `sqlite3` | Zero-dependency; sufficient for task state |
| OpenCode invocation | `subprocess` + OpenCode CLI | Direct CLI is the most reliable integration point |

### Phased Delivery Plan

#### Phase 1: Core Loop Engine (MVP)

- Python daemon with Kanban Watcher + LLM Router + Approval Gateway (Telegram only) + Hands Executor
- Single LLM provider (Gemini API)
- Telegram bot for Manager approval
- Basic state machine (JSON file)
- **Deliverable:** A working end-to-end loop: backlog task → LLM plan → Telegram approval → OpenCode execution → QA loop → Telegram closure approval

#### Phase 2: Manager's Dashboard

- Streamlit local web UI replacing/supplementing Telegram
- Kanban visualization with task cards
- Inline plan rendering with Approve/Reject buttons
- Task history and execution logs

#### Phase 3: Multi-LLM + Advanced Features

- Multi-provider LLM routing (Gemini/Claude/Qwen/OpenAI)
- Parallel task execution (multiple Hands sessions)
- Trace logging (full execution transcripts per task)
- Memory integration (read/write to `mcp-memory-server`)
- Configurable approval policies (auto-approve trivial tasks, require approval for high-risk tasks)

### Security & Compliance Constraints

1. **ZAC Enforcement:** The engine NEVER executes `git add`, `git commit`, or `git push`. All commits go through `custom_context_commit_and_clean_task` MCP tool after explicit Manager approval.
2. **No Browser Automation:** No Puppeteer, Playwright, Selenium, or headless browser components.
3. **No ToS Violations:** All LLM interactions use official APIs with valid API keys.
4. **Approval Gate Integrity:** The engine cannot bypass Step 3 or Step 8 approval gates. A missing approval blocks the pipeline.
5. **Sandboxed Execution:** OpenCode is invoked in the project workspace only. No file modifications outside the workspace.

### Key Brainstorming Findings

- **system_architect:** The highest-leverage architectural change is making the task file the universal record. Adding a transcript section (tool calls, reasoning, metrics) turns it into the eval substrate without new infrastructure. The eval harness should be a new MCP tool, not a Brain-side persona.
- **security_engineer:** Trace recording creates a new sensitive-data surface. Transcripts must be stored locally, git-ignored or sanitized before commit. LLM-judge graders must be bypass-resistant.
- **product_manager:** The Manager's pain point is friction, not desire for full autonomy. The solution is a "Manager's Console" with Approve/Reject buttons, not a fully autonomous system.
- **business_strategist:** This transitions the company from "AI-assisted development" to a "Self-Driving Software Factory." Aligns with leverage-over-effort operating principle.
- **legal_advisor:** All LLM interactions must use official APIs. No scraping. No ToS violations. Trace sanitization doubles as a GDPR/CCPA compliance control.
- **critical_thinker:** The Manager's assumption "I can't access you without a browser" is a false constraint. The Brain is the system prompt + LLM weights, not the browser. Bypass the browser entirely.
